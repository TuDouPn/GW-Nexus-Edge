## 4. 设计正文

### 4.1 当前 AgentScope Adapter 职责（已验证事实）

`nexus-edge-agentscope-adapter`（DEV-0001~0002 建立，55/55 测试）当前职责：
- `AgentscopeAgentExecutionAdapter implements AgentExecutionPort`：start/cancel/resume/stream 四语义；
- `buildSecureAgent()`：官方 HarnessAgent，禁用危险工具 + Memory Hooks，`stateStore(AgentStateStore)` 注入；
- `AgentRuntimeIdentityMapper`：业务 Tenant/Workspace/User/Session → scoped userId/sessionId（稳定/无碰撞/路径安全），
  原始业务 ID 在 RuntimeContext extras（DEV-0002 实证）；
- `ExecutionContextState`：Nexus 持久化执行上下文（workspaceId/tenantId/taskId/userId/sessionId），
  按 taskId 键隔离，resume 时逐项校验（fail-closed）；
- 会话状态（agent_state）与执行上下文经同一个 `AgentStateStore` 接口持久化；
- 事件映射（业务终态、Nexus eventId）、Trace 传播、Secret 经 Reference 解析。

**Adapter 的 `stateStore` 目前只接 JsonFileAgentStateStore（测试）**——`AgentStateStore` 是官方接口，
Redis 官方实现是同一接口的 drop-in（§4.2.1 实证）。

### 4.2 AgentScope 官方 Persistence/Recovery API 实证（Maven Central jar + sources 核验，2026-08-12）

#### 4.2.1 Redis Agent State Store（会话/状态持久化）

- 坐标：`io.agentscope:agentscope-extensions-redis:2.0.1`（BOM 管理）；依赖 agentscope-core/harness 2.0.1、
  jedis 7.4.1、redisson 4.2.0、lettuce-core 6.4.2.RELEASE（POM 实证）。
- 类：`io.agentscope.extensions.redis.state.RedisAgentStateStore implements AgentStateStore`
  （javap 实证：save/get/getList/exists/delete/listSessionIds/clearAllSessions/close）。
  Builder：`keyPrefix(String)` + jedis/lettuce/redisson 客户端二选一 + `build()`。
- **键结构（sources 实证）**：
  - 单状态：`{keyPrefix}{userId}/{sessionId}:{stateKey}`（JSON String）；
  - 列表状态：`{keyPrefix}{userId}/{sessionId}:{stateKey}:list`（List）+ `:list:_hash`（Hash）；
  - 会话键集合：`{keyPrefix}{userId}/{sessionId}:_keys`（Set）。
  - 默认 `keyPrefix="agentscope:session:"`；`userId` 经 `normalizeUser`（路径安全段）。
- **TTL（sources 实证）**：`RedisClientAdapter.set(key, value)` **无 TTL 参数**，RedisAgentStateStore
  **不设过期** → 键永久保留。**TTL 与清理责任归 Nexus Edge**（§4.4）。
- **隔离**：键含 `{userId}/{sessionId}`——配合 DEV-0002 的 scoped 身份（含 Tenant/Workspace/User 维度），
  天然实现 Tenant/Workspace/User/Session 隔离；`keyPrefix` 再加环境/命名空间前缀（如
  `nexus:{env}:agentscope-session:`）。

#### 4.2.2 DistributedStore / Checkpoint / Snapshot（远程执行与沙箱恢复）

- `io.agentscope.harness.agent.DistributedStore`（harness 接口）：`agentStateStore()` + `baseStore()`
  （远程文件系统）+ `sandboxSnapshotSpec()` + `sandboxExecutionGuard()` + `messageBus()` +
  `asyncToolRegistry()`（javap 实证）。
- `RedisDistributedStore.fromJedis(jedis, prefix)`：官方 Redis 实现（javap 实证）。
- `RedisSnapshotSpec extends RemoteSnapshotSpec`、`RedisRemoteSnapshotClient implements RemoteSnapshotClient`
  （upload/download/exists）——**沙箱快照（Checkpoint）机制**，用于远程 Sandbox 执行恢复（Coding 取向）。
- **边界判定（推断，实现时复核）**：V1 经营分析业务 Agent 使用本地 HarnessAgent + State Store 即可满足
  03 §6"业务步骤级恢复"；`RedisDistributedStore` 的 baseStore/snapshot/messageBus/asyncToolRegistry 子集
  面向远程沙箱/异步工具执行（Coding），**V1 经营分析不引入**。Checkpoint（沙箱快照）不作为 OQ-007 的
  V1 通过条件（OQ-007 的 Redis 会话恢复部分可解决；Checkpoint 仍标记待评审，见 §10）。

#### 4.2.3 客户端选择（Lettuce 版本冲突点）

- 扩展 POM 声明 lettuce-core **6.4.2.RELEASE**；SB 4.1.0 BOM 管理 **7.5.2.RELEASE**——reactor 依赖
  调解会解析 7.5.2（BOM 优先）。`LettuceClientAdapter` 在 7.5.2 下的兼容性**未验证**。
- **倾向（推断）**：使用 **Jedis 7.4.1**（扩展官方直接依赖，独立于 SB BOM，无版本冲突）；实现时实证
  Jedis 版在真实 Redis 下工作；Lettuce 7.5.2 兼容作为备选验证项（§11 未验证）。

### 4.3 Nexus Task 与 AgentScope Execution 边界（已验证 + 冻结决策）

| 标识 | 归属 | 语义（实证来源） |
|---|---|---|
| taskId | Nexus | 业务 Task 标识，贯穿全部 Attempt（ADR-0006/DEV-0001） |
| taskAttemptId | Nexus | Attempt 业务主键，UUIDv7 |
| agentId | AgentScope | Agent 实例标识（getAgentId，构建时 UUID）；**不是官方 Execution ID**（ADR-0006） |
| traceId | OTel | 执行链路 trace id |
| RuntimeContext.userId/sessionId | AgentScope | **scoped 身份**（DEV-0002 Runtime Identity） |
| RuntimeContext extras | Nexus | 原始 workspaceId/tenantId/sessionId（DEV-0002） |
| AgentStateStore 键 | AgentScope 接口 | `{prefix}{userId}/{sessionId}:{key}`（§4.2.1 实证） |

- Nexus 持久化业务 Task、Attempt、状态投影、Execution Link（03 §3 task 模块；§6 长任务）。
- **不得复制 AgentScope 内部状态机**（03 §3 task 模块禁止事项）。
- AgentScope 2.0.1 无独立 Execution ID（ADR-0006）；恢复以 (scoped userId, scoped sessionId) + AgentStateStore 会话为准。

### 4.4 Redis 数据结构、Key Scope、TTL 及清理责任（设计）

**键布局（本设计采用）**：
```
{keyPrefix}{scopedUserId}/{scopedSessionId}:nexus_execution_context:{taskId}   ← Nexus 执行上下文（业务）
{keyPrefix}{scopedUserId}/{scopedSessionId}:agent_state                        ← AgentScope 会话状态（官方）
{keyPrefix}{scopedUserId}/{scopedSessionId}:agent_state:list / :list:_hash      ← 官方列表态（如用到）
{keyPrefix}{scopedUserId}/{scopedSessionId}:_keys                               ← 官方会话键集合
```
- `keyPrefix` = `nexus:{environment}:agentscope-session:`（环境级命名空间；生产/测试/本地互不污染）。
- `scopedUserId/scopedSessionId` = DEV-0002 Runtime Identity（含 Tenant/Workspace/User 维度，路径安全）。
- **隔离不变量**：不同 Tenant/Workspace/User/Session → 不同 scoped 身份 → 不同键前缀段，互不可见（§4.2.1 实证结构 + DEV-0002 实证映射）。

**TTL 与清理（Nexus 责任；AgentScope 官方实现不设 TTL——sources 实证）**：
- 会话生命周期由 Nexus 管理：
  - **主动清理**：Task 到达终态（COMPLETED/FAILED/CANCELLED）且业务保留期满足后，Adapter 调用
    `AgentStateStore.delete(userId, sessionId)`（官方接口）清理该会话全部键；
  - **保留策略（设计建议）**：V1 活跃会话保留 ≥30 天、终态任务会话保留 ≥7 天（具体值由业务模块 ADR 定；
    本项先定义责任与机制，不做业务保留期裁决——属后续业务工作项）；
  - **危险操作禁止**：`clearAllSessions()`（按 keyPrefix 全删）禁止在生产调用（只允许受控维护命令）；
  - **keyPrefix 按环境隔离**：清理只作用于本环境前缀，避免跨环境误删。
- **TTL 若需要**：由 Nexus 在业务层执行 `EXPIRE`（经统一 Redis 客户端）或依赖会话清理任务；
  不修改 AgentScope 官方实现。

### 4.5 调用链和恢复时序（设计）

**启动（start）**：
```
startExecution(request)
  → SecretResolver 解析 → ModelAssembler 注册模型
  → AgentRuntimeIdentityMapper → scoped (userId, sessionId)
  → RedisAgentStateStore.save(user, session, "nexus_execution_context:{taskId}", ExecutionContextState)  [业务]
  → HarnessAgent(secure).streamEvents(messages, RuntimeContext(scoped))  → AgentScope 写会话状态到 Redis
```

**服务重启恢复（resume，新 Adapter 实例 + 同 scoped 身份）**：
```
resumeExecution(reference)
  → RedisAgentStateStore.get(user, session, "nexus_execution_context:{taskId}")   [从 Redis 读业务上下文]
  → fail-closed 校验：存在性 / taskId/userId/sessionId/workspaceId/tenantId 逐项与 reference 一致
      / 反序列化有效 / 无跨 Scope（键落在 reference 的 scoped 段）
  → 重新注册模型 + 重建 HarnessAgent（同 scoped RuntimeContext）
  → streamEvents("继续之前的会话") → AgentScope 从 Redis 恢复会话历史 → 新 attemptNo++
```

**时序不变量**：先读+校验 → 再建 Agent（失败路径不遗留未关闭 Agent，DEV-0001 P1-2 保持）；
恢复内容与引用错绑/篡改/缺失 → fail-closed（DEV-0001/DEV-0002 已实现于 ExecutionContextState，Redis 版保持同一语义）。

### 4.6 错误、幂等、并发和 fail-closed 规则（设计）

- **Redis 异常**（连接失败/超时/序列化失败/键缺失）：向上抛异常 → Task 进入 FAILED；**不得伪装为成功**
  （C-8）。日志脱敏（不含 Secret/Key 值）。
- **缺失状态**：resume 时 Redis 中无 `nexus_execution_context:{taskId}` 或 `agent_state` → `IllegalStateException`
  （fail-closed，不静默创建错误上下文；C-5）。
- **损坏状态**：JSON 反序列化失败 / 内容与键不符 → fail-closed（C-5；已实现逐项校验，Redis 版复用）。
- **跨 Scope**：reference 指向的 scoped 段与 Redis 键不一致 / restored 的 workspace/tenant 与引用不符 →
  fail-closed（C-3 隔离 + 负向测试）。
- **幂等（C-6）**：
  - 业务幂等：重复 `startExecution` 由业务层 Idempotency-Key（03 §6：外部副作用依赖 Idempotency Key）；
  - 重复 `resumeExecution(reference)`：每次产生**新 attemptNo**（不重复执行旧 attempt；旧 attempt 状态不变）；
  - `AgentStateStore` 幂等写：同键重复 save 覆盖同会话（官方语义）。
- **并发**：同一 taskId 并发 start/resume 由业务层（Attempt 递增 + 唯一约束）串行化；Adapter 内部
  `handlesByAttemptId` 并发安全（ConcurrentHashMap）；单 Task 单执行源（DEV-0001 P0-2）。
- **清理并发**：终态清理 delete(user, session) 幂等（键不存在即无操作，官方接口语义待实证）。

### 4.11 已验证事实 / 推断 / 未验证项 / 外部阻塞（严格分列）

**已验证事实（jar/javap/sources/POM/既有测试实证）**：
- `agentscope-extensions-redis:2.0.1` 坐标与传递依赖（jedis 7.4.1 / redisson 4.2.0 / lettuce 6.4.2.RELEASE）；
- `RedisAgentStateStore implements AgentStateStore`（Builder: keyPrefix + jedis/lettuce/redisson）；
- 键结构 `{prefix}{userId}/{sessionId}:{key}`（含 `:list`/`:list:_hash`/`:_keys`），默认前缀 `agentscope:session:`，
  userId 经 normalizeUser 路径安全化（sources 实证）；
- **官方实现不设 TTL**（RedisClientAdapter.set 无 TTL；sources 实证）；
- `DistributedStore`/`RedisDistributedStore`/`RedisSnapshotSpec`/`RedisRemoteSnapshotClient` 存在与职责
  （javap 实证：agentStateStore/baseStore/sandboxSnapshotSpec/sandboxExecutionGuard/messageBus/asyncToolRegistry；
  snapshot=沙箱快照 upload/download/exists）；
- 标识边界：taskId/taskAttemptId/agentId/traceId；AgentScope 无独立 Execution ID（ADR-0006/DEV-0001）；
  scoped Runtime Identity（DEV-0002）；AgentStateStore 接口语义（JsonFile 版已验，DEV-0001）。
- 既有 55/55 测试全绿（DEV-0001/0002）。

**推断（待实现时实证，不视为事实）**：
- Jedis 7.4.1 为最稳妥 Redis 客户端选择（独立于 SB BOM，无 lettuce 6.4.2 vs 7.5.2 冲突）；
